# Натхнені Карпатим guidelines для Claude Code

> Дивись мій новий проєкт [Multica](https://github.com/multica-ai/multica) — open-source платформа для запуску та керування coding-агентами з багаторазовими скілами.
>
> Стеж за мною на X: [https://x.com/jiayuan_jy](https://x.com/jiayuan_jy)

Один файл `CLAUDE.md` для покращення поведінки Claude Code, заснований на [спостереженнях Андрея Карпатого](https://x.com/karpathy/status/2015883857489522876) про пастки LLM при кодингу.

---

## Проблеми

З поста Андрея:

> «Моделі роблять хибні припущення замість тебе і просто біжать з ними, не перевіряючи. Вони не керують своєю розгубленістю, не шукають уточнень, не виявляють суперечностей, не показують компроміси, не заперечують коли треба.»

> «Вони реально люблять ускладнювати код і API, роздувати абстракції, не прибирають мертвий код... реалізують роздуту конструкцію на 1000 рядків там, де вистачило б 100.»

> «Вони досі іноді змінюють або видаляють коментарі та код, який недостатньо розуміють, як побічний ефект — навіть якщо це ніяк не стосується задачі.»

---

## Рішення

Чотири принципи в одному файлі, які напряму вирішують ці проблеми:

| Принцип | Що вирішує |
|---|---|
| **Думай перед кодингом** | Хибні припущення, прихована розгубленість, відсутність компромісів |
| **Простота понад усе** | Надмірне ускладнення, роздуті абстракції |
| **Хірургічні зміни** | Сторонні правки, чіпання коду якого не треба |
| **Виконання від цілі** | Левередж через test-first, верифіковані критерії успіху |

---

## Чотири принципи детально

### 1. Думай перед кодингом

**Не припускай. Не ховай розгубленість. Показуй компроміси.**

LLM часто мовчки обирають інтерпретацію і виконують. Цей принцип змушує явно міркувати:

- **Озвучуй припущення явно** — якщо не впевнений, питай, а не гадай
- **Показуй кілька інтерпретацій** — не вибирай мовчки коли є двозначність
- **Заперечуй коли треба** — якщо є простіший підхід, скажи про нього
- **Зупиняйся коли збентежений** — назви що незрозуміло і попроси уточнення

### 2. Простота понад усе

**Мінімальний код що вирішує задачу. Нічого спекулятивного.**

Боротьба з тенденцією до overengineering:

- Ніяких фіч поза тим що просили
- Ніяких абстракцій для одноразового коду
- Ніякої «гнучкості» або «конфігурованості» яку не просили
- Ніякої обробки помилок для неможливих сценаріїв
- Якщо 200 рядків можна написати як 50 — переписуй

**Тест:** чи скаже senior-інженер що це надмірно складно? Якщо так — спрощуй.

### 3. Хірургічні зміни

**Чіпай тільки що мусиш. Прибирай тільки свій бардак.**

При редагуванні існуючого коду:

- Не «покращуй» сусідній код, коментарі чи форматування
- Не рефактори те що не зламано
- Дотримуйся існуючого стилю, навіть якщо сам зробив би інакше
- Якщо помітив непов'язаний мертвий код — згадай про нього, не видаляй

Коли твої зміни створюють «сироти»:

- Видаляй імпорти/змінні/функції які ТВОЇ зміни зробили непотрібними
- Не видаляй вже існуючий мертвий код якщо не просили

**Тест:** кожен змінений рядок має напряму простежуватись до запиту користувача.

### 4. Виконання від цілі

**Визначай критерії успіху. Крути цикл до верифікації.**

Перетворюй імперативні задачі на верифіковані цілі:

| Замість... | Перетвори на... |
|---|---|
| «Додай валідацію» | «Напиши тести для невалідних входів, потім зроби щоб вони пройшли» |
| «Виправ баг» | «Напиши тест що відтворює баг, потім зроби щоб він пройшов» |
| «Рефактор X» | «Переконайся що тести проходять до і після» |

Для багатокрокових задач — озвучуй короткий план:

```
1. [Крок] → верифікація: [перевірка]
2. [Крок] → верифікація: [перевірка]
3. [Крок] → верифікація: [перевірка]
```

Сильні критерії успіху дають змогу LLM крутити цикл самостійно. Слабкі («зроби щоб працювало») потребують постійних уточнень.

## Встановлення

**Варіант A: плагін Claude Code (рекомендовано)**

Всередині Claude Code, спочатку додай маркетплейс:
```
/plugin marketplace add forrestchang/andrej-karpathy-skills
```

Потім встанови плагін:
```
/plugin install andrej-karpathy-skills@karpathy-skills
```

Це встановить guidelines як плагін Claude Code — скіл стане доступним у всіх твоїх проєктах.

**Варіант B: CLAUDE.md (на рівні проєкту)**

Новий проєкт:
```bash
curl -o CLAUDE.md https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md
```

Існуючий проєкт (дописати):
```bash
echo "" >> CLAUDE.md
curl https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md >> CLAUDE.md
```

## Ключова ідея

Від Андрея:

> «LLM виключно добре крутять цикли до досягнення конкретних цілей... Не кажи що робити — дай критерії успіху і дивись як воно йде.»

Принцип «Виконання від цілі» саме це і фіксує: перетворюй імперативні інструкції на декларативні цілі з циклами верифікації.

## Як зрозуміти що воно працює

Guidelines працюють якщо бачиш:

- **Менше непотрібних змін у diff-ах** — тільки запитані зміни
- **Менше переписувань через надмірне ускладнення** — код простий з першого разу
- **Уточнюючі питання до імплементації** — а не після помилок
- **Чисті, мінімальні PR** — без попутного рефакторингу і «покращень»

## Кастомізація

Guidelines розроблені для злиття з проєктними інструкціями. Додай до свого `CLAUDE.md` або створи новий.

Для проєктних правил додай секції на кшталт:

```markdown
## Проєктні guidelines

- Використовувати TypeScript strict mode
- Всі API-ендпоінти мають мати тести
- Дотримуватись існуючих патернів обробки помилок у `src/utils/errors.ts`
```

---

## Примітка про компроміс

Guidelines схиляють до **обережності, а не швидкості**. Для тривіальних задач (очевидний однорядник, помилка друку) — використовуй здоровий глузд. Не кожна зміна потребує повної строгості.

Мета — зменшити дорогі помилки в нетривіальній роботі, а не сповільнювати прості задачі.
